# Нагрузочный тест (ТЗ §11, §13)

Два теста. «Сайт целиком» (17.11.2026) — посетители ходят по страницам, как браузер, через ту же цепочку, что на сервере. «API отдельно» (23.10.2026) — запросы каталога прямо в API, без сайта.

## Сайт целиком (17.11.2026)

`ops/load-site.mjs` — без зависимостей, Node ≥ 22. Каждый посетитель загружает страницу (рендер Next.js), её JS, CSS, шрифты и до 12 фото. Файлы загружаются один раз на посетителя, дальше считается, что они в кэше браузера. После страницы идут её запросы к API: расчёт доставки на странице товара, подсказки поиска, фильтр каталога. Пауза между страницами — 3–8 с.

**Сценарии:**
- **Гость.** Заходит на главную, в каталог или сразу на товар, дальше 3–10 переходов: товар — 45%, каталог — 30%, поиск — 15%, главная — 10%.
- **Покупатель с входом** (20% посетителей):
  1. Анкета из 5 шагов, каждый сохраняется.
  2. Сборка капсулы.
  3. Страница капсулы, второй вариант, замены вещи.
  4. Капсула в корзину.
  5. Оформление с расчётом доставки. Заказ не создаётся.
  6. Ещё 2–4 страницы.

  Вход — по сессиям из `apps/api/scripts/load-users.ts`, без формы входа и её лимитов.

**Ступени:** 50 → 100 → 200 → 400 → 800 одновременных посетителей. Когда посетитель уходит, его место занимает новый — с пустым кэшем и другим адресом.

**Нормы по p95:**
- страница ≤ 800 мс — до последнего байта HTML, это строже «хорошего» времени ответа по web.dev;
- API ≤ 300 мс (ТЗ §11);
- сборка капсулы ≤ 2 с (ТЗ §13);
- фото и статика ≤ 500 мс.

Ошибок 5xx, обрывов и ответов 429 быть не должно.

**Стенд:**
- Mac, 11 ядер.
- API — собранная версия (`node dist/main.js`). Сайт — автономная сборка (`node server.js`), как в Docker.
- PostgreSQL и Redis — на той же машине. Данные — нагрузочная база: 6 250 товаров, 50 000 вариантов, фото — 50 настоящих снимков с превью.
- Сайт обращается к API по сетевому адресу машины, а не по 127.0.0.1, как контейнер сайта в сети docker.
- Caddy заменён небольшим прокси с той же маршрутизацией и постоянными соединениями. Сам `ops/Caddyfile` проверен `caddy validate`.

### Что нашлось и исправлено

1. **Лимиты «на IP» были общими на весь сайт.**
   - **Причина.** API доверял как прокси только loopback. На сервере запросы приходят из контейнера сайта (172.x), поэтому `req.ip` у всех покупателей был один — адрес контейнера.
   - **Последствия.** После 120 просмотров товаров за 10 минут на всём сайте расчёт доставки на странице товара отвечал 429 всем. Так же работали остальные лимиты на IP:
     - вход — 20 за 15 минут, дальше капча или 429 для всех;
     - регистрация — 10 в час;
     - расчёт доставки при оформлении — 60 за 10 минут.

     Учёт просмотров склеивал разных покупателей в одного. В тесте при 50 посетителях было 75 отказов за минуту, при 100 — все 397.
   - **Исправление.**
     - API доверяет loopback и частным сетям (`apps/api/src/bootstrap.ts`). Подменить адрес снаружи нельзя: Caddy заменяет пришедший `X-Forwarded-For`, а порты сайта и API не опубликованы.
     - Страницы передают адрес покупателя в API (`apps/web/src/lib/server-api.ts`).
     - Тест — `apps/api/test/trust-proxy.test.ts`.
2. **Прокси Next.js закрывал соединения.**
   - **Причина.** Все `/api/*`, включая фото, шли через rewrites Next.js. Его прокси открывает к API новое соединение на каждый запрос (`agent: false`) и отвечает `Connection: close`.
   - **Последствия.** При 200 посетителях в TIME_WAIT висело около 11 000 закрытых соединений, ответы ждали по 3,5–13 с. Пропускная способность упёрлась в 330–360 запросов/с и дальше не росла.
   - **Исправление.**
     - Caddy отправляет `/api/*` прямо в API и держит соединения открытыми (`ops/Caddyfile`).
     - API и сайт держат простаивающее соединение 65 с, дольше Caddy (60 с), иначе Caddy мог бы отправить запрос в уже закрытое соединение.
     - Rewrites в `next.config.ts` остались для разработки, где Caddy нет.
3. **Сборка капсулы тянула весь каталог.**
   - **Причина.** Варианты подходящего размера и ростовки отбирались в JS из всех вариантов в наличии — десятки тысяч строк на каждую сборку.
   - **Последствия.** При 400 посетителях API занимал 5–9 ядер, сборка шла 8,5 с (p50), и остальные запросы ждали вместе с ней.
   - **Исправление.** Отбор перенесён в базу: отдельный запрос на каждый слот, только нужные поля. Сборка ускорилась с 830 до 52 мс — медиана по 40 анкетам.
   - **Проверка.** Кандидаты старой и новой выборки совпали в 40 анкетах из 40 (52 901 товар). Капсулы совпали один в один, если в обеих версиях упорядочить строки одинаково. Теперь при равной оценке и цене выбор идёт по id товара, а не по случайному порядку строк в базе.
4. **Выкладка не применяла новый `Caddyfile`.**
   - **Причина.** Файл подключён в контейнер Caddy отдельным файлом. После rsync контейнер продолжал видеть старую версию.
   - **Исправление.** `ops/deploy.sh` пересоздаёт Caddy, если конфигурация в контейнере отличается от репозитория. Перерыв — 1–2 с, только при изменении.

5. **При сбое API каталог, поиск и товар отвечали 404.**
   - **Причина.** Страница не отличала «такой страницы нет» от «API не ответил». Так было и при перегрузке, и при перезапуске API на выкладке.
   - **Последствия.** Поисковик принял бы такую страницу за удалённую и мог убрать её из выдачи.
   - **Исправление.** «404» — только если так ответил API, при сбое — код 500 и экран «Не получилось загрузить страницу» с кнопкой повтора: `pageMissing` в `apps/web/src/lib/server-api.ts`, `app/(shop)/error.tsx`. Главная при сбое по-прежнему открывается без блоков с данными.

**Что это значит для сервера 4 vCPU / 8 ГБ.** Ядро сервера слабее ядра Mac — по опыту в 1,5–2 раза.
- **200 посетителей:** около 1,4 ядра Mac, на сервере это 2–3 vCPU. Запас есть.
- **Следующий потолок — сайт.** Next.js — один процесс, и при 400 посетителях он уже занимал целое ядро Mac. На 800 страницы отвечали 1–3 с, а API оставался быстрым.
- **Ожидаемый предел:** 250–350 одновременных посетителей. Точная цифра — прогоном на сервере (ниже).
- **Если понадобится больше** — второй экземпляр сайта за Caddy. Сейчас не нужно: цель ТЗ — 200.

### Как повторить

**Локально.** Нагрузочная база — раздел «API отдельно» ниже.
- Сборки:
  - API — `pnpm --filter @aesculap/api build`;
  - сайт — `NEXT_OUTPUT=standalone API_INTERNAL_URL=http://<IP машины>:4210 pnpm --filter @aesculap/web build`.

  Сетевой адрес вместо localhost нужен, чтобы сайт обращался к API так же, как в docker.
- Запуск:
  - API — `NODE_ENV=production ALLOW_TEST_PROVIDERS=1 API_PORT=4210`, база `aesculap_load`;
  - сайт — `node .next/standalone/apps/web/server.js`. Предварительно скопировать `.next/static` и `public`, как в `apps/web/Dockerfile`.
- Затем:

```bash
DATABASE_URL=postgresql://aesculap:aesculap@localhost:5432/aesculap_load \
  pnpm --filter @aesculap/api exec tsx scripts/load-users.ts 60 > load-users.json
LOAD_USERS=load-users.json LOAD_ORIGIN=<WEB_ORIGIN API> node ops/load-site.mjs http://localhost:4010
DATABASE_URL=…/aesculap_load pnpm --filter @aesculap/api exec tsx scripts/load-users.ts --clean && rm load-users.json
```

**На боевом сервере перед пилотом** (шаг 1.9 плана; база потом сбрасывается). Тест запускается в сети docker, мимо Caddy: так у каждого посетителя свой адрес. Генератор нагрузки берёт около 0,3 ядра того же сервера.

```bash
cd /srv/aesculap && C="docker compose -f docker-compose.prod.yml --env-file .env.production"
$C exec -T -e LOAD_USERS_ALLOW=1 api npx tsx scripts/load-users.ts 60 > /root/load-users.json
docker run --rm --network aesculap_default -v /srv/aesculap/ops:/ops:ro -v /root/load-users.json:/u.json:ro \
  -e LOAD_USERS=/u.json -e LOAD_ORIGIN=https://<домен> -e LOAD_STAGES=50:60,100:60,200:180,300:120 \
  node:22-bookworm-slim node /ops/load-site.mjs http://web:4000
$C exec -T -e LOAD_USERS_ALLOW=1 api npx tsx scripts/load-users.ts --clean && rm /root/load-users.json
```

**Снаружи через Caddy** — `LOAD_FAKE_IP=0 node ops/load-site.mjs https://<домен>`. Тогда все посетители идут с одного адреса, и расчёт доставки упирается в лимит 120 запросов за 10 минут с IP: такие 429 ожидаемы и ошибкой не считаются.

Тест увеличивает счётчики просмотров товаров. На боевом его запускать до сброса данных перед пилотом.

## API отдельно (23.10.2026)

Машина разработчика (Mac, 11 ядер), PostgreSQL 18 и Redis на той же машине, API — собранная версия (`node dist/main.js`, `NODE_ENV=production`, `connection_limit=30`). На сервере с выделенной БД цифры будут не хуже.

**Данные:** 100 поставщиков, 6 250 товаров, 50 000 вариантов (`pnpm --filter @aesculap/api load:seed` в отдельную базу `aesculap_load`).

### Целевая нагрузка: 200 покупателей

200 соединений, общий темп 70 запросов/с (покупатель кликает раз в ~3 с), кэш каталога холодный на старте.

| Сценарий | p50 | p90 | p97.5 | Ошибок |
| --- | --- | --- | --- | --- |
| Каталог: 20 страниц × 3 сортировки | 55 мс | 132 мс | 235 мс | 0 |
| Фильтры: 120 комбинаций (категория, размер, цвет, цена, сортировка) | 46 мс | 102 мс | 144 мс | 0 |
| Поиск: 30 запросов, включая опечатки и другую раскладку | 89 мс | 203 мс | 235 мс | 0 |
| Подсказки поиска | 52 мс | 109 мс | 237 мс | 0 |
| Карточка товара (200 разных) | 23 мс | 119 мс | 154 мс | 0 |
| Главная | 30 мс | 64 мс | 80 мс | 0 |
| Проверка корзины (10 позиций) | 22 мс | 60 мс | 125 мс | 0 |

Критерий ТЗ — p95 ≤ 300 мс; в таблице более строгий p97.5. Выполнен во всех сценариях.

### Сборка капсулы

20 анкет с разными ростом, размерами, полом, цветотипом и всеми пятью бюджетами (`pnpm --filter @aesculap/api capsule:bench`): **20 из 20** в бюджете и в размере, сборка 0,75–0,95 с при норме 2 с (с 17.11, после переноса отбора размеров в базу, — около 50 мс, раздел «Сайт целиком»). Для бюджета «до 5 000 ₽» пять вещей не помещаются даже по минимальным ценам — подбор убирает аксессуар и обувь и пишет об этом в объяснении.

### Что изменено по итогам

- Список каталога: минимальная цена (с учётом акции) считается в базе и только для сортировки по цене; было — выборка всех вариантов кандидатов на каждый запрос (4,6 с на первую страницу).
- Фильтры (счётчики), порядок выдачи и состав главной кэшируются в Redis на 30–120 с; одновременные промахи по одному ключу ждут один расчёт. Карточки (цена, наличие, видимость) всегда свежие; снятие с витрины, модерация и выплаты сбрасывают кэш сразу.
- Поиск по опечаткам — оператор `<%` вместо функции `word_similarity`, результат кэшируется на минуту.
- Пул соединений к БД: `?connection_limit=30` в `DATABASE_URL` (по умолчанию Prisma берёт 2 × ядра + 1).

### Как повторить

```bash
psql -d postgres -c "CREATE DATABASE aesculap_load OWNER aesculap"
export DATABASE_URL=postgresql://aesculap:aesculap@localhost:5432/aesculap_load
pnpm --filter @aesculap/api exec prisma migrate deploy && pnpm --filter @aesculap/api prisma:seed
pnpm --filter @aesculap/api load:seed
# API на 4200 с этой базой (NODE_ENV=production требует ALLOW_TEST_PROVIDERS=1 без боевых ключей), затем:
LOAD_CONNECTIONS=200 LOAD_RATE=70 LOAD_SECONDS=20 pnpm --filter @aesculap/api load:test
pnpm --filter @aesculap/api capsule:bench
```
